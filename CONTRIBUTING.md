# Участие в разработке

## Процесс

1. Создайте ветку от `main`: `feature/<кратко>`, `fix/<кратко>` или
   `chore/<кратко>`.
2. Внесите изменения; для новой логики добавьте юнит-тесты в `tests/`.
3. Перед коммитом выполните `make check` — он запускает сборку с `-Werror`,
   тесты, санитайзеры и проверку форматирования.
4. Откройте pull request. CI должен быть зелёным; изменения проходят ревью.

## Коммиты

Используется [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <краткое описание>

<необязательное тело: что и почему, а не как>
```

Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`.
Области: имена модулей (`input`, `terminal`, `ui`, …) или `make`, `ci`.

Примеры:

```
feat(input): распознавать X10-отчёты мыши
fix(ui): устранить дрожание времени окончания на ±1 с
refactor(terminal): инкапсулировать состояние raw-режима
```

## Стиль кода

Форматирование задаётся `.clang-format` и проверяется в CI; вручную
выравнивать ничего не нужно — `make format`.

Нужен **clang-format 21.x** — версия зафиксирована, потому что 18.x и 21.x
по-разному считают ширину строки при выравнивании хвостовых комментариев с
не-ASCII (кириллическим) текстом: 18.x измеряет байты, 21.x — визуальные
колонки. Из-за этого 18.x отвергает код, отформатированный 21.x, и наоборот,
поэтому одна и та же версия должна использоваться локально и в CI:

```sh
clang-format --version                       # должно быть 21.x
python3 -m pip install clang-format==21.1.8  # установка, если версия другая
```

Симптом рассинхрона — `format-check` падает на строках вида
`WW_OK = 0, /**< Успех. */` с `[-Wclang-format-violations]`, хотя локально
`make format` ничего не меняет.

Основные правила:

- Стандарт C11, только POSIX; без расширений компилятора.
- Публичные идентификаторы с префиксом `ww_` (функции, типы) или `WW_`
  (макросы, константы enum). Полная таблица — в
  [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
- Все функции, не входящие в публичный API модуля, объявляются `static`.
- Указатели на неизменяемые данные — `const`. Параметры-выходы идут
  последними.
- Функции, которые могут не выполниться, возвращают `ww_status_t`; коды
  ошибок не смешиваются с полезными значениями.
- Нет «магических чисел»: константы именуются через `#define` или `enum`.
- Комментарии объясняют **почему**, а не **что**. Публичные заголовки
  документируются в стиле Doxygen (`@brief`, `@param`, `@return`).
- Логика без побочных эффектов выделяется в чистые функции и покрывается
  тестами; работа с ОС локализуется в `terminal` и `clock`.

## Тесты

- Каркас — `tests/ww_test.h`, внешних зависимостей нет.
- Один файл `tests/test_<модуль>.c` на модуль; набор регистрируется в
  `tests/suites.h` и вызывается из `tests/test_main.c`.
- Имена тестов описывают поведение: `sgr_mouse_release_is_ignored`.
- Тесты не зависят от окружения: часовой пояс фиксируется (`TZ=UTC`),
  реальное время в утверждениях не используется.

## Релиз

Релиз запускается пушем тега — дальше всё делает
`.github/workflows/release.yml`.

1. Убедитесь, что `main` зелёный и содержит все нужные изменения.
2. Поднимите версию в `include/workwatcher/version.h` (`WW_VERSION_MAJOR`,
   `WW_VERSION_MINOR`, `WW_VERSION_PATCH` и `WW_VERSION_STRING` — строка
   обязана совпадать с тегом).
3. В `CHANGELOG.md` переименуйте `[Unreleased]` в `[X.Y.Z] — ГГГГ-ММ-ДД` и
   обновите ссылки-сноски в конце файла.
4. Прогоните `make check`.
5. Закоммитьте, поставьте аннотированный тег и запушьте его (обратите
   внимание: remote называется `WorkWatcher`, а не `origin`):

   ```sh
   git add include/workwatcher/version.h CHANGELOG.md
   git commit -m "chore(release): X.Y.Z"
   git tag -a vX.Y.Z -m "WorkWatcher X.Y.Z"
   git push WorkWatcher main
   git push WorkWatcher vX.Y.Z
   ```

Что делает workflow:

- сверяет тег с `WW_VERSION_STRING` и падает при расхождении (до сборки);
- собирает с `-Werror`, прогоняет юнит-тесты и тесты под ASan/UBSan;
- проверяет, что `--version` печатает версию из тега, а запуск без TTY
  завершается ошибкой, а не зависает;
- упаковывает `workwatcher-X.Y.Z-<платформа>.tar.gz` (бинарник, `README.md`,
  `CHANGELOG.md`) и файл `.sha256`;
- создаёт GitHub Release с описанием из раздела `[X.Y.Z]` файла
  `CHANGELOG.md`. Предрелизы (`vX.Y.Z-rc.1`) публикуются как *prerelease*.

Повторный пуш того же тега обновляет существующий релиз (описание и ассеты
перезаписываются), а не падает. Теги без префикса `v` — исторические `0.0.1`
и `0.0.2` — релиз не запускают: формат только `vX.Y.Z`.

Локально собранный бинарник не публикуется: релизные ассеты всегда
собираются в CI на чистом окружении.

### Платформы

Набор ассетов задаётся `matrix.include` в `release.yml`: Linux x86_64
(`ubuntu-22.04` — чем старее glibc на раннере, тем шире совместимость) и
macOS arm64 (`macos-latest`). Новая платформа добавляется одной записью в
матрицу; `platform` попадает в имя файла.

На macOS скачанный бинарник может быть помечен карантином:

```sh
xattr -d com.apple.quarantine workwatcher
```

## Definition of Done

- [ ] `make check` проходит локально.
- [ ] Новая логика покрыта тестами.
- [ ] Обновлены `README.md` / `docs/ARCHITECTURE.md`, если изменилось
      поведение или структура.
- [ ] Добавлена запись в `CHANGELOG.md` (раздел *Unreleased*).
